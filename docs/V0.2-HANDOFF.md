# DSH host v0.2 — final handoff

Status: **implemented, independently verified (T14 ACCEPT), installed non-destructively.**
Date: 2026-09-30 (Asia/Shanghai). Live session intentionally left running.

## What the user gets

- One platform, starts automatically on the next login.
- Official DSH Web UI loaded unchanged.
- No version picker, no check command, no manual rollback, no per-update user action.
- If the UI crashes, DSH tasks keep running; if DSH crashes, the supervisor restarts it and the UI follows the new URL automatically.
- If a newly installed DSH version is broken, the supervisor automatically falls back to the last known-good DSH runtime against the same `~/.dsh`; the user sees the normal official UI.

## Architecture

```text
systemd --user dsh-host.service  (enabled; starts at next login, Restart=always)
└── supervisor (Node)
    ├── dsh web child (official server, random loopback port)
    │   └── ready URL -> $XDG_RUNTIME_DIR/dsh-host/current-url (0600) + status.json
    └── Electron child (attach mode, sandboxed)
        └── reads current-url, loads the official WebUI, follows URL changes
```

Known-good runtime snapshots live under `~/.local/state/dsh-host/runtimes/`; `known-good.json` and `attempt.json` are atomic, 0600.

## Applied deployment (non-destructive)

- `dsh-host.service`: **enabled, NOT started**.
- `dsh-web.service`: **disabled, NOT stopped**; the live session is still PID 1102.
- `~/.config/niri/config.kdl`: backup at `~/.local/state/dsh-host/install-backups/20260930-003431/niri-config.kdl`; old DSH startup line commented with `// dsh-host-disabled:`; `dsh-electron` window rule appended; `niri validate` valid.
- Manifest: `~/.local/state/dsh-host/install-manifest.env`.

On the next login, `dsh-host.service` starts automatically and becomes the platform. To switch immediately, the single user-approved action is `systemctl --user start dsh-host.service` (this stops the old session via `Conflicts=dsh-web.service`). Rollback: `packaging/install-host.sh --rollback` (then start the old service if needed).

## Application launcher registration (added after review)

- `dsh-host.service` is enabled in the systemd user manager (`WantedBy=default.target`), so the platform starts at login without any launcher action.
- A visible app-launcher entry is installed at
  `~/.local/share/applications/deepseek-harness.desktop` (template:
  `packaging/deepseek-harness.desktop`). It runs
  `systemctl --user start dsh-host.service`, so clicking the app starts/focuses
  the stable platform rather than the old Chrome PWA.
- Icons: `~/.local/share/icons/hicolor/scalable/apps/deepseek-harness.svg`
  (official DSH favicon) and a 256px PNG fallback.
- The old Chrome PWA entry (same display name) is preserved for rollback but
  marked `NoDisplay=true`, so the launcher now resolves to the stable platform.
  Backup: `~/.local/state/dsh-host/install-backups/launcher-<timestamp>/`.
- If rollback is ever needed, remove the `NoDisplay=true` line from the old
  Chrome PWA desktop file and run `update-desktop-database`, in addition to the
  service/niri rollback documented in `docs/DEPLOY.md`.


## GUI close behaviour and tray icon (2026-09-30)

- Closing the window (`X`) hides it to the tray and logs `main window hidden to tray; DSH host keeps running`. The DSH server child is **not** stopped; agent tasks continue.
- Tray menu: `显示 DSH` / `重启 Harness` / `隐藏界面（DSH 后台继续）`. The hide item and window close are equivalent; there is no accidental UI `app.quit()` from the tray anymore.
- Tray icon is now the official DSH icon: `packaging/icon.png` (256px, generated from the official DSH favicon) and `packaging/icon-32.png`; `src/main/main.js` resolves the packaged resource first, then the repo path, and `tray.js` falls back to the embedded icon only if neither exists.
- To fully stop the platform (DSH included) use `systemctl --user stop dsh-host.service`; the desktop launcher then starts it again when needed.
- The currently running UI was restarted without touching the DSH child (verified: DSH PID unchanged across the UI restart).


## Clipboard permission fix (2026-09-30)

The official Web UI uses `navigator.clipboard.writeText()` for copy buttons (and
standard paste events for the composer). The v0.2 permission policy originally
allowed only audio media, so Electron denied `clipboard-read` /
`clipboard-sanitized-write` from the runtime origin. The policy now allows
clipboard permissions from the runtime origin only, while still denying every
other permission and still keeping media audio-only. Tests:
`decidePermissionRequest` / `decidePermissionCheck` matrix plus the real
`installSecurityPolicy` handler wiring. UI was restarted to apply the fix; the
DSH child PID stayed unchanged.
